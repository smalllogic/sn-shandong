# 分类集合页筛选设计建议

## 结论与适用范围

建议采用“属性库 → 叶子分类录入配置 → 集合页筛选配置 → 商品实际值”结构。
叶子分类决定商品允许填什么；任意层级的集合页决定前台展示哪些筛选项。两者必须分开。
这是基于当前代码和公开资料的设计建议，不是经过本站客户实验验证的最优方案。
本次未实现功能，未审计实际商品属性覆盖率。

## 设计依据

- E1：Shopify 官方说明将结构化属性定义与前台筛选来源分开，允许管理员选择来源与调整展示。参考该配置思路，不照搬其平台限制。[官方说明](https://help.shopify.com/en/manual/online-store/storefront-search/search-and-discovery-filters)
- E2：Baymard 公开文章建议同组多选、展示已选条件与选项数量、保留返回时的状态，并区分桌面即时更新和手机明确应用。它是研究机构的公开总结，不提供本站具体用户证据。[文章](https://baymard.com/blog/ecommerce-filter-ui)
- E3：Algolia 文档说明分面可结合 AND/OR，数量需要随条件上下文计算。这支持统计与筛选共用基础商品范围；不表示本站必须采用 Algolia。[官方文档](https://www.algolia.com/doc/guides/managing-results/refine-results/faceting)
- E4：W3C 多滑块模式包含键盘、名称、值范围要求，并指出部分触屏辅助技术存在操作困难。因此本方案优先数字输入框，滑块可后加。[W3C](https://www.w3.org/WAI/ARIA/apg/patterns/slider-multithumb/)

## 后台：三个入口

### 属性库

定义稳定且唯一的代码、多语言名称、数据类型、标准单位、精度、有效范围、枚举选项。
类型包括 number、enum、multi_enum、boolean、interval、text。
属性的类型和单位由属性库统一规定，集合页不能随意改成另一种含义。
已经使用的代码、单位、类型不能无迁移地修改；允许停用，但保留旧值解释能力。

### 叶子分类：商品属性

从属性库选用属性，设置必填、详情显示与录入顺序。价格仍是 sku.price，不复制进规格 JSON。
后台商品表单根据这些配置生成。规则修改前显示受影响商品及缺失数量。
旧商品可以处于“待整理”，不得因新必填规则立即阻止无关字段编辑；发布或完成规范化时执行严格校验。

### 任意分类：集合页筛选

为每个大类、中间分类和叶子分类提供“集合页筛选”标签页。
管理员点击添加筛选项，选择价格或规范属性，设置：

| 配置 | 示例 |
|---|---|
| 开启状态 | 启用 |
| 数据来源 | 属性库中的容量，或系统价格 |
| 前台标题及帮助 | 容量（L） |
| 适用商品类型 | 全部当前类别，或仅冰箱分支 |
| 显示时机 | 始终，或选择适用子类后 |
| 交互方式 | 最低/最高输入、多选框、是/否、目标数值 |
| 匹配规则 | 数值落在输入区间、设备区间包含目标值 |
| 展示顺序、默认展开 | 第 3 项，展开 |
| 选项顺序 | 手动或数值升序 |

只允许与数据类型兼容的交互和运算符，不提供任意 SQL、任意 JSON 路径或自由表达式。
复制其他分类配置可以降低维护量；第一版不自动继承复杂的父级配置。

配置旁显示预览与数据质量：例如容量适用 60 件、已填 52 件、缺失 8 件；大类共 100 件。
适用范围覆盖与字段填写率分开统计，不能把“不适用”与“未填写”混为一谈。
没有有效数据的字段不能成为空壳筛选项；发布前提示原因。草稿配置可保存。

## 大类与子类语义

以“制冷设备”为例：根页优先配置子分类、公开价格、跨类型含义一致的属性。
日产冰量仅适用于制冰机，不应假装是全部制冷商品的公共参数。
建议在根页配置该字段时选择“选中制冰机分支后显示”，进入制冰机后自动出现。
管理员若明确要根页直接展示局部属性，应标注“仅制冰机适用”；应用后无该属性的商品不匹配。
第一版默认用条件显示，减少客户误认为其他设备数据缺失的风险。
字段从何处取值与筛选在哪里显示分开后，根页配置不会强迫全部叶子分类录入同一属性。

## 前台布局建议

桌面延续现有左侧栏：上方为当前分支导航，下方为可折叠的参数筛选。
商品区顶部显示总结果数、排序和可删除的已选条件标签。首版默认展开少量重要项，其余折叠；具体数量要经使用观察调整。
选项选择后局部更新，不移动用户的操作焦点；数字输入使用应用动作或提交事件，避免每个按键刷新。
手机使用筛选按钮打开抽屉，勾选只更新待应用条件与预览数量；“显示 N 件商品”才提交，关闭取消未应用改动。
结果页保留已应用标签，不要求客户重新打开抽屉确认条件。

## 区间筛选不能只有一个含糊的 range 开关

| 商品数据 | 前台输入与名称 | 匹配规则（闭区间） |
|---|---|---|
| 容量 500L | 容量 300–600L | 300 <= value <= 600 |
| 工作温度 [-18,-10]℃ | 所需工作温度 -15℃ | product_min <= target <= product_max |
| 工作温度 [-18,-10]℃ | 需完整覆盖 -16 至 -12℃ | product_min <= requested_min 且 product_max >= requested_max |
| 工作温度 [-18,-10]℃ | 需与 -12 至 -8℃有交集 | product_min <= requested_max 且 product_max >= requested_min |

温度筛选默认目标值包含；完整覆盖只在业务确实需要时配置；交集不是默认规则。
尺寸必须先拆成宽、深、高等数值，不能对“600×700×800mm”字符串直接做范围比较。
客户可以只填下限或上限；0 是有效值；负温度有效；下限大于上限时显示错误，不静默交换。
每项注明单位及包含边界。滑块只能作为输入框的补充，并验证键盘与触屏辅助技术。

## 统一筛选逻辑

- 同属性枚举多选：OR；不同筛选组：AND。多值属性如需全部满足，必须使用另一种清晰的业务标签。
- 未填写属性的商品在未筛此字段时保留，筛此字段时不匹配；缺失、0、false 分开处理。
- 先限制 Sku.visible 和当前分类全部后代，再执行搜索、价格、属性过滤，最后统计、排序、分页。
- 结果数量和分面统计来自全部候选商品，不是当前 20 条分页商品。
- 每个枚举选项数量：应用其他组条件，暂时排除本组条件后，统计具有该值的不同商品数。选项数是该值匹配量，不是假装为“再点击一次后的总量”；同组可重叠，不能简单相加。
- 0 件未选选项置灰或隐藏；已选选项即使为 0 也保留，允许撤销。已应用组不得自动消失。
- 无结果保留输入与条件，提供逐项删除、清空；不擅自放宽条件。
- 切换到不同子类时，只保留仍兼容的筛选项，并提示哪些条件被清除。
- URL 保存 category_id/kind、locale、q、filters、sort、page；条件改变重置 page；后退恢复状态。
- 前后台均校验字段白名单、类型和允许的运算符；非法输入返回可理解错误，不假装已成功过滤。

## Rails 实现结构（建议新增）

| 结构 | 职责 |
|---|---|
| SpecificationDefinition / SpecificationOption | 定义类型、单位、翻译、选项 |
| CategorySpecification | 叶子分类录入规则；(category_id, definition_id) 唯一 |
| CategoryFilter | 任意分类集合页配置；来源恰为 price 或一个 definition；同页同源不重复 |
| Sku.specification_values | 新的规范 JSON；保留原 specifications 作为迁移来源 |
| SpecificationValidator | 商品保存校验与迁移状态约束 |
| CatalogFilterConfig | 解析当前集合页的可用筛选及适用范围 |
| CatalogQuery | 构造可见性、分类、搜索、过滤和排序查询 |
| CatalogFacets | 结果数、选项数与可用范围 |
| CategoriesController | 读取参数、调用服务、返回页面和错误 |
| Stimulus + Turbo | 表单交互、手机抽屉、局部刷新及导航状态 |

控制器不能只更新现有 skus_list：筛选数量和条件标签也必须同步。
可改用包住筛选与列表的 catalog_results Frame，或 Turbo Streams 同时更新多个区域；加载时保留焦点及正在输入的值，防止旧响应覆盖新选择。
当前分类树链接也只指向 skus_list；切分类应完整更新页面上下文，避免标题、Banner 和筛选配置仍停留在旧分类。
已有代码：app/models/category.rb、app/models/sku.rb、app/controllers/categories_controller.rb、app/views/categories/index.html.erb。
当前尚无属性库、分类属性关系、CategoryFilter 或规范值字段。

商品 JSON 只存标准值；显示名和单位读取属性库。PostgreSQL 的 JSONB 精确值和数值范围索引需按实际查询设计，不能认为一个通用索引能覆盖全部范围查询。
本站本地 SQLite、生产配置 PostgreSQL：查询层隔离差异，先保证两种数据库行为一致；选择性建立常用属性索引，实测后再决定是否增加属性值表或搜索服务。
当前不需要因研究分面概念而立即引入 Algolia。

## 迁移与交付顺序

1. 盘点七大类下叶子分类的实际属性与单位，得到待确认映射，不改原数据。
2. 建属性库、分类录入配置、旧数据预览转换与缺失清单。
3. 增加所有分类的集合页筛选配置、条件适用范围和后台预览。
4. 对一个大类及两个差异明显的子类试点，验证根页和子类规则。
5. 完成价格、枚举、数字范围、目标值区间筛选；验证手机和桌面。
6. 其余分类使用同一机制逐步启用，不以全量数据一次清洗为上线前提。

## 验收任务与限制

验收：管理员给大类增加电压，给制冰机配置日产冰量；客户在大类筛电压，选制冰机后出现日产冰量；用容量上下限与温度目标值获得正确产品；零结果可撤销；前进后退与语言切换保留条件；不可见商品不计数；跨分类移动后不泄露不兼容条件。
通过给定任务观察少量真实客户是否理解字段与范围语义，再决定默认展开、布局和刷新方式；没有本站实验结果，不能宣称转化率提升。
